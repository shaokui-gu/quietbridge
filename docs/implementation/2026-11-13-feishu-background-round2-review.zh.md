# 飞书后台点击与 AX 填写第二轮复核

依据：用户提供的第二轮验证报告、原生操作元数据日志及源码。本轮没有操作飞书或重试写入。

## 结论

- 当前 Space 的飞书主窗后台点击后，搜索窗出现，结合界面观察可确认点击产生预期效果；回执本身仅表示事件已派发。另一 Space 的情况未测。
- 搜索框 AX 写入后读回包含测试字符串，但伴随原有字符和换行，不能算精确替换；首次恢复原值失败。报告追加的第三次执行中，AX 层读回测试文本，但用户观察到屏幕上没有可见文字，结果区也未进入查询态；恢复原值后两次 AX 读回与原值一致。不能由单次恢复成功推断始终可回滚，也不能据此认为查询或发消息能力通过。
- 报告早期两阶段和第三次执行的 end 回执只显示捕获停止已请求；独立原生日志随后分别在 18:58:20.101、18:59:37.732 和 19:25:32.464 记录 `captureStopCompleted`、`stopConfirmed=true`，证明这些捕获最终停止。
- 用户补充的直接观察：搜索框出现后、点击飞书图标之前，飞书主窗口、搜索框与 WorkBuddy 在同一个桌面；点击飞书图标后，飞书主窗口和搜索框一起出现在第二个桌面。这不是仅凭时间相关性推断出来的现象。现有日志没有记录点击前后飞书各窗口的 Space 归属，也没有足够证据解释触发原因；宿主和预览的 Space 信息不能代替目标窗口的前后状态。
- 报告追加的单独共享对照中未观察到窗口 bounds 变化；该次基线里 WorkBuddy 正在使用但回执标记 `onScreen=false / currentSpace=false`，这些字段在该次观察中不足以判定实际桌面位置。报告关于旧搜索窗口触发切桌的说法是待验证的推测，不能替代用户上述观察。
- 该轮还出现持续约 31.5 秒的预览层级校验失败及多次短暂失败。此前的 100ms 防闪修改针对短暂过渡，不能证明本轮所有显示异常已经解决。

## 源码改动

`setValue` 成功派发后读取一次 AX 值，分别报告精确匹配、不匹配或不可读；不记录回读内容，也不自动重写。即使即时值匹配，应用实际响应仍需另行观察。回读异常不会把已派发的写入标记为未派发；这些改动不代表飞书 Electron 搜索输入能力已经修复，也尚未打包。

## 后续对照测试

用户反馈后续测试通过：飞书没有切换到其他桌面，输入框显示正常。用户认为此前异常与当时发现的飞书自身 bug 有关，并非本次工具操作造成。后续《飞书搜索框人工输入与AX写入对照报告》记录 AX 写入文字可见、人工清空后恢复基线；但该次 AX 写入后搜索结果未变化，人工输入时则出现查询结果，因此文字可见不等于搜索已执行。报告中未验证捕获最终停止。

用户随后反馈，多次测试中搜索结果列表的目标选项点击无响应，聊天窗口中的输入框点击、输入及发送也未生效；不据此否定此前搜索入口曾展开的观察，也不将其扩大为所有控件均不可用。最近两次主窗后台点击的原生元数据表明 AX 动作因后台焦点保护被跳过，鼠标移动、按下和松开通过 `SLEventPostToPid` 派发；回执没有证明目标应用实际接收。现有信息不足以将这些点击与用户所述每一项操作逐一对应，亦不能确定无响应的根因或证明改变投递路径不会抢焦点。

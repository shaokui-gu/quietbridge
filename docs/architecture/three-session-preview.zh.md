# QuietBridge：三会话并行与卡片预览

状态：2026-11-08，0.6.5（88）测试包已实现三会话路由、独立执行进程和卡片预览。
此前 0.6.4 为单活动任务、单预览。真实 Workbuddy 三会话连续 30 分钟验收仍待安装后完成。

## 1. 系统能力与当前限制

macOS ScreenCaptureKit 通过独立 SCStream 与 SCContentFilter 捕获窗口，支持多个共享流。
Apple 的 SCContentSharingPicker.maximumStreamCount 明确提供应用共享选择器的流数量限制。
这个属性控制选择器入口，不是 QuietBridge 的任务配额，也不表示系统硬性最多三路。

- [Apple：SCStream](https://developer.apple.com/documentation/screencapturekit/scstream)
- [Apple：maximumStreamCount](https://developer.apple.com/documentation/screencapturekit/sccontentsharingpicker/maximumstreamcount-2kuaa)

三路是本产品首版并行支持上限。实际帧率、内存和稳定性需要在支持的系统与设备上实测，
不能用 API 存在代替本机三路流和真实 Agent 端到端验收。

0.6.4 的限制来自唯一 activeTaskId、原生预览独占租约、SpacePreview.shared 单实例、
共享调度/捕获状态及浏览器单任务通道。0.6.5 以可信调用凭据、会话私有状态、独立原生
执行进程与独立扩展通道替换这些限制；保留跨会话目标仲裁。

## 2. 首版交付范围

- 一个 QuietBridge 应用最多三个活动执行会话，总配额跨宿主统一计算。
- 同一个 Workbuddy 的三个独立会话也包含在范围内，不要求分别运行三个宿主应用。
- 每路分别拥有绑定、快照、浏览器命令、共享流、超时与停止状态。
- 先验收不同目标，例如浏览器专用窗口、计算器、另一个测试应用。
- 同一窗口或标签不允许两个会话同时写入；第二个申请返回明确目标占用。
- 同一目标应用的不同窗口，只有后台投递及应用级共享状态经过验证后才开放并行；
  未验证场景按目标进程仲裁，不将“同一个 Workbuddy”误解为任意同进程窗口均可安全操作。
- 第四路返回容量已满及已有槽位状态，不抢占、不排入可能迟到执行的隐藏队列。

## 3. 扑克牌式预览

三个会话各自保持真实共享，在宿主右上角组成一个卡片组。
卡片切换是本地展示行为，不改变任何会话的目标或调用归属。

| 场景 | 交互 |
| --- | --- |
| 只有一路 | 沿用现有全框画面、玻璃底、连续圆角和阴影，无常驻顶部标题 |
| 两到三路 | 其余卡片向左下错开，露出可点击的会话标签与应用图标 |
| 切换 | 点击露出的卡片或紧凑切换入口，将其画面移到最前；显示当前项及总数 |
| 操作进行中 | 各 Agent 继续操作自己的目标，不因收到工具动作强制切换用户选中的卡片 |
| 关闭/结束一项 | 仅回收该项卡片与流，选择另一现有项；其余共享保持原代次 |
| 卡片拖动 | 整组临时移动，保留现有 30 秒回吸规则；宿主移动/缩放时立即重新吸附 |
| 缩放 | 继续只有左下角缩放，按整个卡片组外接边界限制，不能越出宿主右侧 |

预览面板采用非激活行为；切换不激活宿主或目标应用、不移动物理鼠标、不切换 Space。
玻璃用于容器，视频保持清晰。关闭一项与关闭全部必须使用不同、明确的操作语义，
不能把结束共享或结束某一任务藏在普通卡片切换里。

前卡建议 15fps，后卡建议 5fps；这些是待实测的初始预算，不是已验证承诺。
后卡不暂停捕获、不复用前卡的帧、不用旧截图冒充实时共享。用同一流的配置更新帧率，
切卡不重建流。某任务要求操作前观察时，只检查其自身流及目标状态，与用户选中哪张卡无关。
资源不足时返回明确状态，不能静默停止后台共享。

UI 实现前先在原 Figma 文件中补充单卡、三卡堆叠、切换、某项结束和容量已满状态，
保留此前已确认的圆角、阴影、跟随与临时拖动规则。

## 4. 必须同时完成的运行时工作

1. 核实真实 Workbuddy 三会话是否拥有独立 MCP 连接；共享连接必须有可信逐调用上下文。
   PostToolUse 的事后身份只能关联停止，不能当作下一次工具调用的路由依据。
2. Broker 分配三个有界执行槽，建立真实连接/宿主身份与目标写租约。
   禁止从模型自报名称、前台或最后一次 hook 猜会话归属。
3. 私有任务上下文与受管 Worker 分开。AX 卡死时回收所属 Worker；管理服务持续响应。
   只为每个 socket 创建一个面板不能解决共享执行器致命错误影响全部任务的问题。
4. 预览组管理器持有每路捕获流和宿主锚点，卡片展示层单独选择前卡；
   截图、快照和操作检查从请求上下文查找所属捕获，不读取“当前展示卡片”。
5. 浏览器 observer、assignment、候选、命令去重、结果、建窗及子标签按执行会话分路。
   一个会话停止只清理所属通道，保留用户页面和其他会话。
6. 延续 0.6.4 的保护参与者聚合：A 停止不撤销 B/C，最后一个参与者退出才全局收尾。

## 5. 验收门槛

- 三个独立窗口流同时取得有效首帧，持续运行；记录实际帧率、CPU、内存和掉流。
- 同一个 Workbuddy 三会话同时执行至少 30 分钟；浏览器与原生目标互不占用全局任务槽。
- A 结束、取消、超时或 Worker 崩溃，B/C 的输入资格、流和预览代次保持有效。
- 三张卡片反复切换不重建流、不切换目标；后台两路仍获得有效帧。
- 用户持续操作其他应用时保持焦点、物理鼠标和 Space，测试回执与实机观察一致。
- 同目标冲突与第四路容量拒绝可复现；拒绝之后不产生迟到输入。
- 真实宿主身份路由缺口必须明确记录；未通过之前不发布“三会话并行已支持”。

## 6. 0.6.5 实施与验证记录

- Workbuddy PreToolUse 生成一次性凭据，绑定真实 session/request/call 与完整工具参数；
  共享 stdio 连接按凭据分配至最多三个 Python 执行进程。凭据过期、重放、改参均在执行前拒绝。
- 各会话文件位于 `sessions/<sha256>/`；根注册表通过内核所有者锁确认活跃任务并仲裁目标。
- 每个原生连接拥有独立执行子进程、AX 句柄与捕获状态；共享 Broker 只管理共享流、预览及保护聚合。
- 浏览器扩展 0.4.1 使用独立 channel worker；存储、任务分配、命令去重及 CDP 所有者分别维护。
- 卡片组按宿主窗口分组，前卡 15fps、后卡 5fps；切换通过原流配置更新，保持各任务绑定。
  控制面板需明确选择会话；会话结束后清空选择，不能自动改选其他任务后发送操作。
- 本机真实三原生客户端测试通过：杀死 A 的执行进程，B/C 原句柄可继续读取，原共享流代次不变且帧数增长。
- 自建三窗口共享及卡片切换实测通过：各路画面更新，切换未重建流；停止第一路后另两路继续更新；
  前台 PID 未变化，物理鼠标未移动。此测试不代表真实 Workbuddy 30 分钟交叉操作已经验收。
- 独立应用目标和 Chrome 专用窗口是首版范围；同一普通应用不同窗口仍按 PID 保守互斥。DSH 适配仍待实现。
